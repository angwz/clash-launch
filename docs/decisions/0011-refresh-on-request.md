# 0011 · 请求订阅时按需拉取

- 状态：已采纳（2026-11-26，反馈 #119）
- 范围：修订规范第 13.3 节「订阅请求只读缓存，不触发拉取或渲染」与 [architecture](../design/architecture.md)「快照」一条

## 背景

节点订阅与规则源按间隔在后台拉取（普通用户最短 30 分钟），客户端更新订阅时拿到的可能是几十分钟前的节点与规则。维护者要求客户端请求订阅时，上游超过 60 秒没拉取就立即重新拉取，使最终订阅保持最新。

## 决定

| # | 内容 | 理由 |
|---|---|---|
| 1 | 请求一份配置时，检查它用到的节点订阅与规则源：最近一次尝试拉取距今超过 `CLASH_LAUNCH_REFRESH_ON_REQUEST`（默认 60 秒，0 关闭）就拉取，并同步重新生成这份配置 | 维护者的要求；以「最近一次尝试」计时，上游持续失败时也至多每个间隔试一次 |
| 2 | 请求最多等 3 秒；来不及就返回最近一次成功的结果，拉取与生成在后台继续 | OpenClash 探测订阅信息的超时是 5 秒，超时会换 UA 重试；客户端不能因上游慢而失败 |
| 3 | 拉取失败或新结果没通过内核检查时，照旧提供上一次成功的结果 | 与定时拉取相同，客户端永远不会收到空配置或坏配置 |
| 4 | 同一份配置的并发请求只刷新一次，其余等同一次的结果 | 避免多个客户端同时更新时重复拉取上游 |
| 5 | 交给客户端（provider）模式的订阅不在服务器拉取 | 客户端自己拉取订阅地址，服务器的快照不进入这份配置 |
| 6 | 开放注册（未经邀请）的用户，间隔取 60 秒与其最短拉取间隔中较大的一个；管理员与受邀用户为 60 秒 | 出站边界（[0003](0003-direct-fetch-and-invites.md)）：陌生用户不能借反复请求自己的订阅链接让服务器频繁访问任意上游 |
| 7 | 不引入新依赖：并发合并用进程内的表实现 | `golang.org/x/sync` 等依赖受 [0001](0001-deviations-from-spec-1.0.md) #17 约束 |

## 影响

- 订阅响应在上游过期时多出最多 3 秒的延迟；上游很快时通常几百毫秒。
- 上游被访问的频率由客户端的更新频率决定，但每个源至多每 60 秒一次。
- 多实例部署时各实例分别合并并发，同一上游可能被每个实例各拉一次。
