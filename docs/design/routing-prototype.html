逐条判断

想法判断怎么落地，或者为什么要改
默认显示全部粒子v4 赞成 粒子改为三种模式：全部（默认）始终显示所有粒子，追踪时只是把被追踪的那个放大、加标签；聚焦在悬停或追踪时让其余粒子淡出；关。选择保存在账号的偏好里。系统开启「减少动态效果」时只能选「关」。
按不同用户的配置智能展现v4 能做，用确定的规则 可以，但我建议的「智能」是一组写明阈值的规则，不是模型推断：同一份配置永远得到同一张图，可以写单元测试，界面上用一行「智能视图」说明用了哪些画法、为什么，每一项都能手动改回。详见下一节。
粒子颜色淡一点v3 赞成，并且要换色 只调淡还不够：v2 用绿色表示直连、红色表示拦截，在红绿色弱（约 8% 的男性）眼里几乎一样（模拟后色差只有 5.8，低于可分辨的 8）。v3 改用三种降了饱和度的流向色：薰衣草紫经代理、湖青直连、陶橙拦截。另外，请求在命中规则之前是灰色，被规则认出后才慢慢染色，画面里大部分时间只有少量颜色。光点更小、拖尾更短、外圈光晕几乎去掉，同屏上限从 90 降到 70。
未分类经代理直连拦截
追踪框悬停出现 ×，一键清空v3 赞成 框里有内容时，鼠标移上去或聚焦时出现 ×；点它清空输入并结束追踪，焦点留在输入框里，可以直接输入下一个。键盘上按 Esc 效果相同。
3 层或更多层能否良好展示v3 改了布局 能，但不能「每层一列」。你的 groups.toml 按全部引用关系算最深 7 层，按默认成员算只有 4 层；7 层来自备用成员之间的交叉引用。v3 改为按默认路径分层，候选成员按需显示，详见下一节。原型里可以切换 1 层、3 层和你的 23 个组。
多个规则集拖成一个合集 赞成，有约束 与 domainrouter_v2 的发布结构一致（每个合集最多 domain、ipcidr、classical 三条，按此顺序连续排列）。合集的成员共享一个走向，输出仍是连续的几条 RULE-SET。约束：IP 成员默认加 no-resolve，否则排在中间时会让后面每个未命中的域名都先做一次 DNS 解析；不编译成 OR 逻辑规则，否则客户端里看不出命中的是哪个成员。
在面板里改策略组的模式 赞成 只提供官方 v1.19.33 的四种：select、url-test、fallback、load-balance；relay 已被移除，由「链式代理」承担。v3 在切换处加上每种类型适合什么、不适合什么，以及按参数给出的提醒（见「节点策略怎么选」）。
粒子流动、左侧进入规则集、右侧从出口离开 赞成，有约束 粒子是示意，不是流量：服务器看不到你的真实流量，粒子的多少不能暗示「这条线流量大」；但每个粒子的路线按真实匹配结果计算。Canvas 绘制，画面不可见时暂停，系统开启「减少动态效果」时关闭，可一键关掉。
智能展现

按配置的形状选择画法

用户的配置差别很大：有人 10 条规则、5 个节点，有人 ACL4SSR 完整版 70 条规则、40 个组，有人订阅交给客户端拉取，服务器根本看不到节点。图的画法由一个纯函数 planView(图数据, 视口, 用户偏好) 决定：先量出配置的形状，再按下表逐项选择。每一项都写进「智能视图」那一行，并能在偏好里改回。

层级

层很深时怎么画：跟着默认路径分层

用你的 groups.toml（参考提交 2c812f9）实际算了一遍：

23个策略组
74条成员引用（含正则选中的节点）
7层：按全部引用的最长链，例如 漏网の鱼 → 节点选择 → 香港专线 → 新加坡专线 → 新加坡高速 → 美国专线 → 美利坚高速
4层：只沿每个组的默认成员走，例如 YouTube → 节点选择 → 香港专线 → 香港高速 → 节点

7 层几乎全是备用路径：「香港专线」的第二个成员是「新加坡专线」，而几乎每个专线和高速组都把「美国专线」作为最后的备份。平时流量只走每个组的第一个成员（select 的默认、fallback 的优先），所以图的骨架应该按这条路径来排。

  • 分层：没有任何组引用它的组，以及被规则直接使用、且不是任何组默认成员的组，放在第一列；其余按「沿默认成员到节点还要走几步」从右往左排，直接连节点的组对齐到最后一列。只当备份的组（如 ACL4SSR 的各地区组）因此不会挤进第一列。你的配置分成 4 列：业务组 → 节点选择 → 专线 → 高速，每列一种角色。
  • 候选成员按需显示：每个组默认只画一条实线（默认成员）。悬停或选中一个组时，才画出它的候选成员（虚线）；也可以打开「显示全部候选」看全貌。你的配置平时只画 23 条组内连线，而不是 74 条。url-test 与 load-balance 的成员地位相同，始终全部画出。
  • 列多时变紧凑：3 列及以上时，组的类型标签缩成一个字（选、速、备、均），名称完整保留。列数再多就在卡片内横向滚动，规则列和出口列不缩。
  • 同列与反向的候选线：候选成员可能在同一列甚至左边一列（例如高速组的备份是美国专线），这类线只在聚焦时画出，绕到列间的空隙里，不穿过别的行。
  • 追踪卡片永远完整：无论图怎么折叠，追踪结果都逐层列出每个组、它的类型和这一层的选择。
节点策略怎么选

「自动选择没有想象的好」不是错觉

我读了 mihomo v1.19.33 的实现（adapter/outboundgroup/urltest.go、adapter/adapter.go），url-test 优化的是「到测速地址的延迟」，不是「你用起来的体验」。具体是这样选的：

源码里的行为带来的感受
延迟是经节点向测速地址发一次 HEAD 请求的耗时；默认包含建立连接、代理握手和 TLS 握手。开启全局 unified-delay 后改为在同一连接上再发一次，只计第二次。握手重的协议显得更慢；测的是到 Google 边缘节点（gstatic）的距离，不是到 ChatGPT、Netflix 等目标的距离。
比较时只用最近一次测速结果（LastDelayForTestUrl 取历史的最后一条），不是平均值。一次偶然的快或慢就决定排名，容易选到「刚好测得快」的节点。
不测带宽、丢包、稳定性。延迟最低的节点可能晚高峰限速或丢包，看视频、下载反而卡。
默认每 300 秒测一次；lazy 默认开启，组闲置时跳过测速。连接失败累计到一定次数才提前测速。两次测速之间节点变差不会立即切换；闲置后第一次使用的是旧结果。
tolerance 默认 0：只要别的节点比当前的快哪怕 1 毫秒，下一次就切过去。节点来回跳，出口 IP 跟着变，AI、流媒体、银行等对 IP 敏感的服务会要求重新验证或风控。
切换只影响新连接，已有的长连接仍留在旧节点。下载或通话中途不会因为「切到更快的」而变快。

按场景选（建议，非源码结论）

AI、流媒体、银行：select 固定节点，或 fallback 按你的顺序；出口 IP 稳定比快几毫秒更重要。
普通浏览与下载：url-test，但把 tolerance 设到 50–100 毫秒，避免来回跳。
只要能用：fallback，平时固定在首选，坏了才换；它只判断「能不能连」，不判断快慢。
多连接大流量：load-balance 选「按目标固定」（consistent-hashing），不要用「轮流」。

放到你的结构里

你现在的写法已经是稳健的那一种：专线用 fallback（跨地区按偏好顺序）、高速用 select（地区内手动）。如果想要「地区内自动、跨地区按顺序」，可以只把四个高速组改为 url-test，配合 tolerance: 50 左右与全局 unified-delay: true；同一地区内切换不会改变出口地区。AI 与流媒体组保持 select。很多订阅自带的「自动选择」是把所有地区的节点放进一个 tolerance 为 0 的 url-test，这正是体验不稳的常见来源。

  • 测速地址用 HTTPS：源码在测速失败时会提示，部分机场会劫持 HTTP 测速地址；你的配置用的是 https://www.gstatic.com/generate_204，没问题。
  • 第三方分支的 Smart 组：vernesong 的 mihomo 分支提供 Smart 策略组，可以用 LightGBM 模型预测节点权重。它不在官方内核里，本站按官方语义生成配置，不提供这个类型；想试需要换用那个分支的内核。
  • 落到产品里：组详情的类型切换处显示「适合 / 不适合」，并按参数给出提醒（容差为 0、只有一个成员、闲置不测速等）。提醒只是提示，不会改你的配置。

一键追踪约 30 个常见网站，表格列出各自走向。任何一次追踪都可以「固定为期望」，以后每次应用、上游更新时自动复核，不符合时提示。这借鉴自 Tailscale 策略文件的 tests。

交互细节

拖动之外，每个操作都有不用鼠标的做法

  • 改走向：把规则拖到策略组，或拖到「直连」「拦截」；也可以在详情面板的「走向」下拉框里选。
  • 改优先级与组合集：拖到另一规则行的上沿或下沿是插到它前后；拖到行的中间是并入它的合集。详情面板里有「提前」「推后」「拆出」，相邻且走向相同的规则集会提示「合并为合集」。兜底的 MATCH 永远在最后。
  • 改策略组：点组打开详情，四个类型一键切换，参数随类型出现，旁边是适用场景与提醒；成员可以「设为首选」（改变默认路径，图会随之重新分层）或移除，也可以把出口或别的组拖进来，会形成循环的拖动直接拒绝。
  • 追踪框：悬停出现 × 清空，Esc 同样清空；回车开始追踪。
  • 草稿：所有改动先进草稿，底部条用一句话列出每处改动。点「应用」才写入配置，随后照常生成预览并做内核检查。
  • 聚焦：悬停或选中任一行，只保留与它相连的路径和粒子，其余变淡；组被聚焦时显示它的候选成员。
  • 手机：窄屏不画连线和粒子，改为分组列表；追踪结果仍是逐步卡片。
存成什么

应用之后，分组、合集与规则顺序归你所有，内容仍来自上游

第一次在地图上点「应用」时，把规则源展开后的分组与规则复制进配置的 routing 段，此后由它决定输出，上游只是起点。规则集里具体有哪些域名，仍由 rule-providers 的地址从上游获取。

# 配置文档（示意，字段名在实施时定稿）
routing:
  from: { ref: domainrouter, at: 2026-11-15T08:00:00Z }   # 从哪个规则源、哪一版开始
  rules:
    - bundle: Direct                                       # 合集：一个走向，成员按 domain → ipcidr → classical 输出
      sets:
        - { url: …/release/clash-domain/Direct.mrs, behavior: domain }
        - { url: …/release/clash-ipcidr/Direct-ipcidr.mrs, behavior: ipcidr }
        - { url: …/release/clash-classic/Direct-classic.yaml, behavior: classical }
      to: DIRECT
    - set: …/release/clash-domain/ChatGPT.mrs
      to: 🗨️ ChatGPT
    - geoip: CN
      to: DIRECT
    - match: 🐳 漏网の鱼
  groups:
    - name: 🛫 香港专线
      type: fallback
      members: [🎇 香港高速, 🧊 新加坡专线]
      url: https://www.gstatic.com/generate_204
      interval: 97
  checks:                                                  # 固定下来的期望
    - { host: chatgpt.com, via: 🗨️ ChatGPT }
  • 合集的自动识别：同一来源中同名的 domain、ipcidr、classical 三件套相邻且走向相同时，自动识别为合集；其他相邻同走向的规则集只提示，不自动合并。
  • 上游更新：记下上游快照，之后的变化与你的改动做三方比对，不冲突的逐条采纳，冲突的列出双方，不自动合并。
  • 与现有层级的关系：routing 取代规则源展开这一步，表单层与原始编辑层仍在它之上合并；生成的 YAML 顺序与格式不变，用 golden 测试锁定。
凭什么可信

追踪用的是 mihomo 自己的匹配代码

mihomo 的控制接口只有 GET /rules，没有「测一个域名命中哪条」的接口，所以追踪在服务器上做。项目已以 Go 模块依赖 github.com/metacubex/mihomo v1.19.33，许可同为 GPL-3.0，可以直接调用内核的 rules.ParseRule 与 rules/provider 的解析与匹配（含 MRS），判断与客户端逐条一致。

  • 新包 internal/match：输入配置与一次请求，输出命中路径与依据。纯函数，可以写 golden。
  • 规则内容：由 internal/source 按站点白名单、SSRF 防护、大小上限下载并缓存，按用户限频。
  • 不替你查 DNS：域名没被域名类规则认出时显示两条分支；也可以直接输入 IP。
  • 运行时的选择：select 当前选了哪个、url-test 测出哪个最快，只有客户端知道。图上按「默认第一个」画实线，url-test 的成员一律画虚线并注明「测速决定」。
  • 先验证再动手：第 0 步确认内核的规则集结构可以不联网地从字节加载，并实测内存与追踪耗时。
怎么画

SVG 画轨道，Canvas 画粒子，不引入画布库

  • 为什么不用 Svelte Flow / React Flow：它们用元素的 style 属性定位节点，本站 CSP 是 style-src 'self'，引入就得放宽。这里的布局可以算出来，连线写进 SVG 的几何属性，CSP 不限制。
  • 流向色：四个独立的 token（未分类、经代理、直连、拦截），浅色与深色各一套，都用调色板校验脚本检查过亮度区间、饱和度下限、色盲模拟色差与对比度。不复用站内的成功、错误状态色。
  • 粒子：带短拖尾的小光点，沿预先采样的路径移动；进入规则集前为灰色，命中后在 0.35 秒内过渡到流向色；被拦截时在「拦截」处轻轻散开。一个 requestAnimationFrame 循环统一更新与绘制，按设备像素比渲染。
  • 无障碍：拖动都有菜单替代；地图另有表格视图；颜色从不单独表达含义，同时有文字、线型与追踪卡片。
