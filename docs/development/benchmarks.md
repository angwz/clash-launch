# 存储层基准

千万级数据下热点查询的实测记录（需求 R14b），后续每项数据库优化都以这里的数字为准。数字只记实测值，换机器、换版本后重新测量并整体替换本页。

## 怎么测

```sh
go run ./tools/dbbench -dsn "postgres://postgres:<密码>@127.0.0.1:55432/postgres?sslmode=disable" -keep   # 新建库、迁移、灌数据、测量
go run ./tools/dbbench -dsn "…" -db cl_bench_<时间>                                                    # 复用保留的库：只执行新迁移并重新测量
```

- 每次新建空库并执行全部迁移，用 `generate_series` 灌数据后 `VACUUM ANALYZE`（相当于生产环境 autovacuum 之后的状态）。
- 每条查询先取一次执行计划（不带 `ANALYZE`），再**真实执行 3 次并读完全部结果**，取墙钟时间的中位数（缓存已热）。这是应用实际等待的时间，包含把结果传到客户端。
- 查询语句与 `internal/store` 保持一致，改 SQL 时同步 `tools/dbbench`。订阅分析另有一张端到端表：直接调用 `store.EachRequest` 与 `service.Analyzer`，计入扫描与 Go 侧汇总。
- 数据只用文档地址与虚构名称。分布：`u1` 是重度用户，占订阅明细的 20%（200 万行）、审计 20 万条、与 `u2` 之间 20 万条消息；其余数据均匀分布在 1 万个用户上，时间均匀落在最近 180 天。

> [!WARNING]
> **不要用 `EXPLAIN ANALYZE` 的执行时间当耗时。** 它对每个计划节点的每一行计时，在这台 Windows 机器上会把返回大量行的查询放大几倍到上百倍（未读数实际 6 ms，`EXPLAIN ANALYZE` 报 700 ms；`TIMING OFF` 则与墙钟一致）。2026-11-20 第一轮基准用的就是这种方法，下文「第一轮」一节的数字因此整体偏大，只能用来比较同一轮内的前后，不能与本页其余数字比较。

| 表 | 行数 | 占用（含索引） |
| --- | ---: | ---: |
| `sub_requests` | 10,000,000 | 3879 MB |
| `audit` | 2,000,000 | 347 MB |
| `messages` | 1,000,000 | 302 MB |
| `users` | 100,000 | 30 MB |

环境：本机 PostgreSQL 17.12（Windows x64 便携版，默认配置，`shared_buffers` 128 MB），2026-11-20。绝对值只在同一台机器上可比。

## 结果

迁移 0016 之后（2026-11-20）。

| 查询（对应方法） | 中位耗时 | 计划要点 |
| --- | ---: | --- |
| 订阅分析：重度用户近 30 天，约 33 万行（`Stats.EachRequest`） | 488.8 ms | 仅索引扫描 `sub_requests_analytics` |
| 订阅分析：重度用户全部 180 天，200 万行 | 3710.6 ms | 同上 |
| 订阅分析：普通用户近 30 天 | 0.7 ms | 同上 |
| 订阅分析：最近 100 条请求（`Stats.LatestRequests`） | 1.1 ms | 倒序索引扫描 `sub_requests_at` |
| 链接请求记录第一页（`Stats.Requests`） | 0.7 ms | 倒序索引扫描 |
| 短链接最近访问，50 个短链接（`Stats.LastByShort`） | 0.7 ms | 每个短链接一次索引下探（部分索引 `sub_requests_short`） |
| 清理一批过期明细（`Stats.PruneRequests`，只看计划） | — | 按 `sub_requests_at` 取一批 1 万行 |
| 审计：个人总数，数到 10,001（`Audit.Paged`） | 2.0 ms | 仅索引扫描 `audit_owner` |
| 审计：个人第 1 页 | 0.2 ms | 倒序主键扫描 |
| 审计：个人第 1000 页（`OFFSET` 9,990） | 80.7 ms | 倒序主键扫描 |
| 审计：全站总数，数到 50,001（`Audit.PagedAll`） | 7.0 ms | 顺序扫描到上限即停 |
| 审计：全站最后可达的第 1000 页（`OFFSET` 49,950） | 7.0 ms | 倒序主键扫描 |
| 未读消息数（`Messages.Unread`） | 6.3 ms | 合并反连接 |
| 与某人的未读数（`Messages.UnreadFrom`） | 3.0 ms | 仅索引扫描 `messages_unread` |
| 会话第一页（`Messages.Thread`） | 1.0 ms | 两个方向各走一次 `messages_pair`，按时间合并 |
| 最近消息（`Messages.Recent`） | 0.7 ms | 发出与收到各取一页再合并 |
| 发送频率检查（`Messages.SentSince`） | 0.7 ms | 仅索引扫描 |
| 用户搜索（`Users.Search`） | 2.4 ms | `pg_trgm` 位图扫描 |
| 管理页用户列表第 1000 页（`Users.Paged`，`OFFSET` 49,950） | 15.7 ms | 按用户名索引扫描 |

订阅分析端到端（与 `/api/v1/analytics` 相同的调用：流式读出 → 汇总 → 最近 100 条）：

| 场景 | 请求数 | 中位耗时 |
| --- | ---: | ---: |
| 重度用户近 30 天 | 330,989 | 662.2 ms |
| 重度用户全部 180 天 | 1,997,870 | 3763.2 ms |
| 普通用户近 30 天 | 165 | 1.6 ms |

其中 Go 侧汇总 33 万条约 129 ms（`BenchmarkAnalyzer`，约 31 MB 临时分配），其余是数据库读取与传输。原写法只读最新 5 万行、超出即截断；同一台机器上读这 5 万行要约 350 ms（psql 计时）。

覆盖索引 `sub_requests_analytics` 约 1 GB，替换了 492 MB 的 `sub_requests_owner`：`sub_requests` 由 3171 MB 增至 3879 MB。

## 第一轮（2026-11-20，`EXPLAIN ANALYZE` 计时）

迁移 0013–0015 与改写 SQL 前后的对比。数字因逐行计时偏大（见上文警告），只用于看同一行的前后变化；改写的依据是执行计划本身（整体排序、全表分组、无界计数变为索引下探或有界扫描），这在新方法下同样成立。

| 查询 | 之前 | 之后 | 改了什么 |
| --- | ---: | ---: | --- |
| 会话第一页 | 1250.9 ms | 2.2 ms | 两个方向各走一次 `messages_pair` 索引、按时间合并，不再 OR 后整体排序 |
| 最近消息 | 1184.5 ms | 1.4 ms | 同上，发出与收到各取一页再合并 |
| 短链接最近访问 | 4896.7 ms | 4.0 ms | 每个短链接一次索引下探；原写法要把重度用户 28 万条经短链接的请求全部分组 |
| 审计：个人总数 | 909.2 ms | 214.5 ms | 只数到 10,001；超过显示「10,000+」 |
| 审计：全站总数 | 9614.3 ms | 1067.6 ms | 只数到 50,001 |
| 审计：全站最深一页 | 6489.6 ms（第 10000 页） | 530.2 ms（第 1000 页） | 页码上限 1000 |
| 用户搜索 | 46.2 ms | 17.2 ms | PostgreSQL 上 `pg_trgm` 索引 |

## 还没解决

- **超长范围的订阅分析**：重度用户一年的明细（约 400 万行）估计要 7–8 秒，仍在 30 秒语句超时以内。再大一个量级时，改为写入时按小时预汇总。
- **用户列表的 `OFFSET`**：10 万用户时第 1000 页约 16 ms，暂不需要改为键集分页。
- **按月分区**：明细已有保留期与按批清理，分区留到单表再大一个量级时再做，届时需要在真实数据副本上演练迁移。
