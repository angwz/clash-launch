# 存储层基准

千万级数据下热点查询的实测记录（需求 R14b），后续每项数据库优化都以这里的数字为准。数字只记实测值，换机器、换版本后重新测量并整体替换本页。

## 怎么测

```sh
go run ./tools/dbbench -dsn "postgres://postgres:<密码>@127.0.0.1:55432/postgres?sslmode=disable" -keep   # 新建库、迁移、灌数据、测量
go run ./tools/dbbench -dsn "…" -db cl_bench_<时间>                                                    # 复用保留的库：只执行新迁移并重新测量
```

- 每次新建空库并执行全部迁移，用 `generate_series` 灌数据后 `VACUUM ANALYZE`（相当于生产环境 autovacuum 之后的状态）。
- 每条查询运行 3 次 `EXPLAIN (ANALYZE, BUFFERS)`，取执行时间的中位数（缓存已热）。查询语句与 `internal/store` 保持一致，改 SQL 时同步 `tools/dbbench`。
- 数据只用文档地址与虚构名称。分布：`u1` 是重度用户，占订阅明细的 20%（200 万行）、审计 20 万条、与 `u2` 之间 20 万条消息；其余数据均匀分布在 1 万个用户上，时间均匀落在最近 180 天。

| 表 | 行数 | 占用（含索引） |
| --- | ---: | ---: |
| `sub_requests` | 10,000,000 | 2771 MB |
| `audit` | 2,000,000 | 304 MB |
| `messages` | 1,000,000 | 218 MB |
| `users` | 100,000 | 24 MB |

环境：本机 PostgreSQL 17.12（Windows x64 便携版，默认配置），2026-11-20。普通磁盘上顺序扫描明显偏慢（审计表 300 MB 全表计数要近 10 秒），绝对值只在同一台机器上可比。

## 结果

每条查询 3 次中位数。「之前」是 2026-11-20 优化前的写法与索引（迁移 0012）；「之后」是迁移 0013–0015 与改写后的 SQL。

| 查询（对应方法） | 之前 | 之后 | 改了什么 |
| --- | ---: | ---: | --- |
| 会话第一页（`Messages.Thread`） | 1250.9 ms | **2.2 ms** | 两个方向各走一次 `messages_pair` 索引、按时间合并，不再 OR 后整体排序 |
| 最近消息（`Messages.Recent`） | 1184.5 ms | **1.4 ms** | 同上，发出与收到各取一页再合并 |
| 短链接最近访问（`Stats.LastByShort`） | 4896.7 ms | **4.0 ms** | 每个短链接一次索引下探取最大时间（部分索引 `sub_requests_short`）；原写法要把重度用户 28 万条经短链接的请求全部分组 |
| 审计：个人总数（`Audit.Paged`） | 909.2 ms | **214.5 ms** | 只数到 10,001；超过显示「10,000+」 |
| 审计：全站总数（`Audit.PagedAll`） | 9614.3 ms | **1067.6 ms** | 只数到 50,001 |
| 审计：全站最深一页 | 6489.6 ms（第 10000 页） | **530.2 ms**（第 1000 页） | 页码上限 1000，`OFFSET` 最多 49,950 |
| 用户搜索（`Users.Search`） | 46.2 ms | **17.2 ms** | PostgreSQL 上 `pg_trgm` 索引，昵称任一段走索引 |
| 清理一批过期明细（`Stats.PruneRequests`） | 全表扫描（之前没有清理） | 按 `sub_requests_at` 取一批 | 新增：明细默认保留 400 天，每批 1 万行 |
| 订阅分析：重度用户近 30 天（`Stats.Range`） | 2092.7 ms | 1732.6 ms | 未优化：要把 5 万行明细读进内存聚合，需改为数据库内聚合（R14c 剩余部分） |
| 订阅分析：普通用户近 30 天 | 7.1 ms | 7.7 ms | — |
| 链接请求记录第一页（`Stats.Requests`） | 2.3 ms | 2.2 ms | — |
| 未读消息数（`Messages.Unread`） | 646.9 ms | 704.4 ms | 新增部分索引 `messages_unread`；样本数据有三分之一未读（重度用户约 3.3 万条），计数本身就慢；真实场景未读数很少，未单独测量 |
| 与某人的未读数（`Messages.UnreadFrom`） | 297.3 ms | 370.4 ms | 同上 |
| 管理页用户列表第 1000 页（`Users.Paged`） | 563.9 ms | 558.5 ms | 未优化：仍用 `OFFSET`，10 万用户时可以接受 |
| 发送频率检查（`Messages.SentSince`） | 0.4 ms | 0.2 ms | — |

新增索引让三张大表变大：`sub_requests` 2771 → 3171 MB，`messages` 218 → 302 MB，`audit` 304 → 347 MB。

## 还没解决

- **订阅分析读明细进内存**：重度用户一次分析约 2 秒，且超过 5 万行会截断。下一步是在数据库里按天、小时、国家、客户端聚合（R14c 剩余部分）。
- **用户列表的 `OFFSET`**：10 万用户时第 1000 页约 0.6 秒；用户数再大一个量级时改为键集分页。
- **按月分区**：明细已有保留期与按批清理，分区留到单表再大一个量级时再做，届时需要在真实数据副本上演练迁移。
